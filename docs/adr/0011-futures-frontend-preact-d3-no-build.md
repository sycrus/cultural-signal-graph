# Futures UI: Preact + htm + signals and D3, vendored, no build step; the stepper stays vanilla

The app has two frontend stacks on purpose. The forecast stepper (`static/app.js`) is vanilla JS that re-renders template strings, with Cytoscape for the Graph tab: it is a linear form-and-review flow and that is enough. Futures mode (`static/futures/`) is a live, many-view UI. One exploration state drives the Scroll and five lenses, fills in over SSE, and supports undo, edits and selection across views. Hand-written DOM updates don't scale to that, so it uses Preact + htm + @preact/signals for state and components, and D3 (SVG) for every lens's geometry. All of it is vendored under `static/vendor/` and loaded as ES modules through an import map, with **no build step**, so the app still starts with a single command (`uv run python -m cultural_signal_graph.server`) and needs no Node toolchain.

**Consequences:** with an unbundled module graph, the browser fetches each module separately, so a page that mixes a fresh module with a stale cached one crashes. Static files are therefore served `Cache-Control: no-cache` (they revalidate and get a 304 when unchanged). Two stacks also means two styling paths; the planned design system (#46) is token-first CSS custom properties so one `tokens.css` can reskin both stacks plus the D3 and Cytoscape fills.

**Considered options:** rewriting the stepper in Preact too (rejected: churn on a working flow for no user-visible gain); React with a bundler (Vite) (rejected because it adds a Node build to a Python project and breaks single-command startup); vanilla JS for futures too (rejected: keeping many views in sync by hand is where bugs breed); Cytoscape for the futures views (rejected because the lenses need custom geometry, such as a time-positioned Scroll, wedges, quadrants and curves, rather than a force graph). Cytoscape stays on the forecast Graph tab.
